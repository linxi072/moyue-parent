# 不可忽视条件（硬性约束）

> 本文档记录项目开发、测试、部署过程中**不可绕过、不可忽视**的硬性约束。任何新需求、新代码、新脚本在落地前必须先对照本文档检查。违反约束的改动一律不允许合入。

## 约束一：项目中禁用 Docker

**生效日期**：2026-09-14（主人指令）

### 约束内容

本项目**全面禁用 Docker 及一切依赖 Docker 的技术**，包括但不限于：

| 禁用项 | 说明 |
|---|---|
| Docker / Docker Compose | 不得用于基础设施部署（MySQL / Redis / Nacos / ES / MailHog 等一律原生安装） |
| Testcontainers | 不得用于任何测试（相关测试已 `@Disabled`，见下） |
| Dockerfile / 镜像构建 | 不得新增；部署采用裸机 + 启动脚本方式 |
| CI/CD 中的 Docker 执行器 | 未来搭建流水线时不得选择 Docker-based runner |

### 已落地的禁用措施

1. **测试（已完成 H2 改造，2026-09-16）**：原 4 个 Testcontainers 流程测试已全部改造为 **Spring Boot Test + H2（MySQL 兼容模式）** 并撤销 `@Disabled`，现已真实执行：

   | 模块 | 测试类 | 用例数 | 状态 |
   |---|---|---|---|
   | `moyue-content` | `com.moyue.read.BookshelfFlowTest` | 4 | ✅ 全绿 |
   | `moyue-social` | `com.moyue.im.ImMessageFlowTest` | 4 | ✅ 全绿 |
   | `moyue-social` | `com.moyue.blog.BlogLikeFlowTest` | 3 | ✅ 全绿 |
   | `moyue-commerce` | `com.moyue.points.PointsOrderFlowTest` | 6 | ✅ 全绿 |

   **H2 改造落地方式（后续新流程测试照此办理）**：
   - 连接串统一形如
     `jdbc:h2:mem:<db>;MODE=MySQL;DATABASE_TO_LOWER=TRUE;CASE_INSENSITIVE_IDENTIFIERS=TRUE;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE`
     —— 并发用例必须再追加 `;LOCK_TIMEOUT=20000`，否则 H2 默认锁等待过短会把"业务并发冲突"误报成锁超时。
   - 各模块 `src/test/resources/application-test.yml` 覆盖数据源与 Flyway 配置，用例以 `@ActiveProfiles("test")` 激活。
   - **H2 与 MySQL 的关键差异：H2 的索引名在 schema 内全局唯一，MySQL 只在表内唯一。** 因此 Flyway 迁移脚本不能直接喂给 H2，需经 `tools/gen-h2-schema.py` 生成等价 schema 落到各模块 `src/test/resources/db/h2/`。
   - 用 `@TableLogic` 承接的逻辑删除在 H2 上行为与 MySQL 一致，无需特殊处理。

2. **脚本**：`scripts/start-all.sh`、`scripts/smoke-test.sh` 中的 `docker compose up -d` 提示已改为原生部署提示。

3. **依赖（已清理，2026-09-16）**：3 个模块 pom test scope 中的 `org.testcontainers:testcontainers` 依赖，以及根 POM 的 `testcontainers.version` 属性，均已随 H2 改造完成一并移除。**不得再次引入。**

- 若未来确需容器化，必须由主人显式撤销本约束并更新本文档，任何人不得自行解除。

## 约束二：逻辑删除必须逐实体显式声明 `@TableLogic`

**生效日期**：2026-09-16（本约束由测试基线工作暴露的系统性缺陷引出）

### 约束内容

本项目 `application.yml` 中的全局 `logic-delete-field` 配置**处于注释状态（未启用）**。因此 MyBatis-Plus **不会**自动把 `deleteById` / `removeById` / `delete(...)` 翻译成 `UPDATE ... SET is_deleted = 1`，而是**退化为物理 `DELETE`**。

**凡 `isDeleted` 字段承载逻辑删除语义的实体，必须在该字段上显式声明：**

```java
/** 逻辑删除：0 否 / 1 是 */
@TableLogic(value = "0", delval = "1")
private Integer isDeleted;
```

（参照 `moyue-system` → `SysUserEntity` / `SysRoleEntity` / `SysMenuEntity` / `SysDeptEntity` / `SysDictTypeEntity` 的既有写法。）

### 为什么必须显式声明

缺注解会导致三个连锁后果，且都**不报错、只静默错**：

1. **物理删行** → 唯一键（如 `uk_user_book`、`uk_user_product`）不再被占用，"删除后再新增"直接成功，绕过原本设计的"复活旧记录"分支。
2. **复活分支变成不可达死代码**：配套的 `revive()` 原生 `UPDATE ... SET is_deleted = 0` 永远命中不到已删行。
3. **软删除语义破产**：历史数据、审计、统计全部丢失，且无法通过查询 `is_deleted=1` 找回。

### 唯一豁免：业务侧自维护逻辑删除的实体

若 Mapper 明确注释"逻辑删除为业务侧维护（`update is_deleted=1`），不使用物理 delete"，则该实体**不加** `@TableLogic`，以免改变其查询语义。当前属此类的有：

- `moyue-risk` → `com.moyue.risk.sensitive.SensitiveWordEntity`
- `moyue-risk` → `com.moyue.risk.report.ReportEntity`

新增豁免必须在该 Mapper 类注释中写明理由。

### 给开发者的提醒

- 新增实体时，只要表里有 `is_deleted` 列且业务上需要软删除，**第一时间**加 `@TableLogic`，不要依赖"全局配置会兜住"。
- 评审时若看到 `deleteById`，必须回查对应实体是否已有 `@TableLogic`。
