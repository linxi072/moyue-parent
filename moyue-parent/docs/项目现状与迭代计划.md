## 1. 评审范围与方法

  - 实现深度核查：逐模块 Read 关键 `Service`，区分「真实业务逻辑」与「空壳/桩/TODO」；
  - 跨服务链路：核对 Feign `@FeignClient` 与实际调用、共享表依赖；

## 2. 总体架构与模块地图

```
moyue-parent
├── moyue-common/            # 基础设施（5）
│   ├── moyue-common-core        # R<T>/ResultCode/BizException/Constants/PageResult/全局异常
│   ├── moyue-common-security    # JwtProvider / HeaderInterceptor / @RequiresRoles·@RequiresPermissions / PreAuthorizeAspect
│   ├── moyue-common-redis       # MoyueCacheAutoConfiguration + CacheNames（前缀 moyue:）
│   ├── moyue-common-mybatis     # MP 分页插件自动装配
│   └── moyue-common-migration   # Flyway V1–V15（实际落地，README 称 V1–V13），全服务共享库
├── moyue-api/               # Feign 契约（8，均带 FallbackFactory）
│   └── account/content/social/commerce/search/message/risk/ai
├── moyue-gateway/           # 8080 网关：JwtAuthGlobalFilter 鉴权 + 显式 lb:// 路由 + docs 聚合
├── moyue-auth/              # 8090 独立认证：登录/注册/刷新（BCrypt + JWT + Redis refresh）
└── moyue-modules/           # 业务服务（9）
    ├── moyue-account/   8081  用户资料
    ├── moyue-content/   8082  书城 book / 章节 chapter / 阅读书架 read / 文件 files / 完结申请
    ├── moyue-social/    8083  评论 comment / 博客 blog / 即时通讯 im（WebSocket）
    ├── moyue-commerce/  8084  积分 points / 商城 merch / 作者稿酬 author（查询桩）
    ├── moyue-search/    8085  检索 book·chapter·qa（ES）+ 推荐 + 全量重建
    ├── moyue-system/    8086  RBAC/字典/配置/日志/监控/代码生成 + 运营公告 + 打赏 + 统计 + XXL-Job
    ├── moyue-message/   8087  站内信 + 渠道 SPI（邮件真/短信·推送桩）+ 触达记录
    ├── moyue-risk/      8089  机审(敏感词 AC 自动机)/人工审核/举报/敏感词管理
    └── moyue-ai/        8097  AI 客服（关键词规则引擎 + 会话落库 + QA 索引）
```

**鉴权模型（双层，已核实）**：
1. 网关 `JwtAuthGlobalFilter`（`@Order(-1)`）校验 Bearer 令牌（jjwt HS256，验签），通过后将 `userId`/`role` 注入下游请求头 `X-User-Id` / `X-User-Role`（证据：`moyue-gateway/.../filter/JwtAuthGlobalFilter.java`）。
2. 业务服务内 `HeaderInterceptor` 读取该头装配 `SecurityContextHolder`，由 `PreAuthorizeAspect` 执行 `@RequiresRoles`/`@RequiresPermissions`；`AdminRoleInterceptor` 拦截 `/api/v1/admin/**`（仅 role=3）。下游**信任网关注入的头**，不在本服务重验 JWT（证据：`moyue-common-security/.../security/HeaderInterceptor.java`、`JwtProvider.java`）。

## 5. 需要深度开发的功能（Top 7）

> 优先选当前明显薄弱、只有空壳、或链路未打通者。每个给出「为什么值得做」+「大致实现方向」。

### ① 稿酬结算与打款闭环（P0，最高优先）
- **为什么值得做**：平台商业化与作者留存的生命线。现状严重残缺——只有「打赏分成 70%」在打赏支付时自动落库（`RewardService.settleAuthorIncome`），订阅分成、买断、结算单、打款状态机全部缺失，`AuthorService` 仅是只读桩，作者「我的稿酬」无法提现。这是已知最大业务断点（时序图已明示为设计假设）。
- **大致实现方向**：
  - 涉及模块：`moyue-commerce`(`com.moyue.author` 由查询桩扩展为结算服务)、`moyue-system`(`operation` 写分成/结算)、新增或对接支付域（微信/支付宝，或复用 `moyue-commerce` 支付能力）。
  - 关键技术点：① 新增 `settlement_order` 表与状态机（待结算→已结算→已打款，幂等）；② 订阅/买断分成规则引擎（当前 `AUTHOR_SHARE_RATIO` 仅打赏 70%，需扩展 incomeType=1 订阅/3 全勤/买断）；③ 对账：以 `reward_order`/`subscription` 为源聚合 `author_income`；④ 收敛「`commerce.author` 与 `system.operation` 共享 `author_income` 表」的耦合——建议改为事件/Feign，而非双映射同一表；⑤ 打款对接支付渠道并落流水，失败可重试/对账补结。

### ② AI 客服真实化：接入 LLM + RAG（P1）
- **为什么值得做**：能力缺口最明显。全仓无任何 LLM 客户端，`KeywordRuleReplyEngine` 仅 10 条硬编码规则 + 兜底，无法处理真实咨询、无多轮上下文、无意图理解；「智能域」名不副实。对话已落库并建 `moyue_qa` 索引，具备做 RAG 的数据基础。
- **大致实现方向**：
  - 涉及模块：`moyue-ai`（新增 LLM 适配层 + `AiReplyEngine` 新实现，保留关键字引擎作兜底/转人工前缀）、`moyue-search`(`moyue_qa` 召回)。
  - 关键技术点：① 抽象 `AiReplyEngine` 新增 `LlmReplyEngine`（接入 DashScope/Qwen 或 OpenAI 兼容网关，密钥环境变量化，走 `MOYUE_*` 配置）；② 以 `moyue_qa` 索引做向量/关键词混合召回做 RAG 上下文；③ 多轮会话上下文拼接（当前 `AiService` 仅存消息，未拼上下文）；④ 转人工闭环：命中兜底/低置信时经 `moyue-message` 或 `moyue-social` 转人工；⑤ 异步索引 hook 已具备，可复用。

### ③ 触达渠道补全：真实短信 + 推送（P1）
- **为什么值得做**：运营触达半截。站内信、邮件已真，但短信/推送为桩（仅打日志返回 pending），消息中心无法真正触达移动端用户；且 `UserDTO` 缺 email/deviceToken，邮件默认也只能靠请求带 `targetEmail`。
- **大致实现方向**：
  - 涉及模块：`moyue-message`(替换 `SmsChannelSender`/`PushChannelSender` 实现)、`moyue-account`(`UserDTO`/实体补 `email`/`deviceToken` 字段，Flyway 加列)、`moyue-api-account`(同步 DTO)。
  - 关键技术点：① 短信接阿里云/腾讯云短信网关（模板+签名）；② 推送接 APNs/FCM/厂商通道，按 `deviceToken` 路由；③ `MessageDispatchClient` 已就绪，渠道 SPI 零改业务代码即可插拔；④ 渠道记录(`message_channel_record`)已有，可直接观测送达。

### ④ 推荐算法个性化（P1）
- **为什么值得做**：当前 `RecommendService` 仅按 `status∈{1,2}` + `hotScore`(点击+收藏×3)/`updateTime` 排序，无个性化，新用户与老用户看到完全一样的「推荐位」，留存与付费转化天花板低。
- **大致实现方向**：
  - 涉及模块：`moyue-search`(召回/排序)、新增用户行为/画像采集（点击、收藏、阅读时长已在 `bookshelf`/`read_duration`、打赏）。
  - 关键技术点：① 兴趣画像（类目偏好/作者偏好）由行为日志聚合；② 召回：ES 向量(`dense_vector`)或标签召回 + 热门/新品保量；③ 排序：简单 CTR 预估或规则加权；④ 冷启动兜底沿用现有 hot/latest；⑤ 可借 `StatService` 现有聚合 SQL 扩画像。

### ⑤ 章节定时发布调度闭环（P0，修复悬空 TODO）
- **为什么值得做**：`ChapterService.publish` 定时场景置 `status=1` 等调度器，但无 JobHandler 接管，作者设置的「定时发布」永远不会自动上线——功能名存实亡，属已写一半的断点。
- **大致实现方向**：
  - 涉及模块：`moyue-system`(新增 `ChapterPublishJobHandler`，XXL-Job Admin)、`moyue-content`(`ChapterService` 暴露被调度调用的发布/索引方法)。
  - 关键技术点：① JobHandler 扫描 `publish_time` 到点且 `status=1` 的章节，置 2 并触发 `syncChapterIndexIfPublished`；② 幂等（重复调度安全）；③ 失败告警/重试；④ XXL-Job Admin 为可选组件，需确保部署（README 标注可选/8088）。

### ⑥ 内容安全处置闭环 + 统计看板（P1）
- **为什么值得做**：机审(敏感词 AC)已真实落地是亮点，但「审核→处置→通知」未成闭环：举报/人工审核裁决后未通知被处理方与举报人；无命中统计/审核工作量看板；仅文本敏感词，无图片/涉政识别。合规与平台安全基线不足。
- **大致实现方向**：
  - 涉及模块：`moyue-risk`(审核裁决后触发通知 + 统计)、`moyue-message`(`MessageDispatchClient` 发处置通知)、`moyue-system`(统计/看板)。
  - 关键技术点：① `ModerationService` REJECT/REVIEW 裁决后，经消息分发通知作者/用户；② 举报处置状态流转与「已处理/已驳回」回执；③ 敏感词 `hit_count` 已有，补管理端看板；④ 图片/ OCR 涉政识别可后续接内容安全云服务（替换/增强本地引擎）。

### ⑦ 测试体系补齐（P0/P1，质量基线）
- **为什么值得做**：4 个核心流程(Testcontainers)用例 `@Disabled`，且单测高度不均（search/risk/system/ai 有，auth/account/commerce/social/comment/message 几乎无）。无质量护栏，后续深度开发极易引入回归，且「禁用 Docker」约束下必须走 H2。
- **大致实现方向**：
  - 涉及模块：全模块；以 `moyue-system` 既有 H2 测试为范本。
  - 关键技术点：① 4 个 `@Disabled` 用例改 H2（`@DataJpaTest`/内存库或 H2 + Flyway）；② 为 commerce(points/merch 并发防超卖)、auth、social(im/comment)、message 补关键路径单测；③ 可选：基于 `moyue-contract` 生成 TS 的契约测试；④ CI 去 Docker runner（不可忽视条件约束）。

## 6. 薄弱点 / 技术债 / 明显缺口

1. **稿酬链路未打通（最大业务断点）**：仅打赏分成(70%)自动落库；订阅分成/买断/结算单状态机/打款全部缺失；作者端为只读桩。详见 §3.4、§5-①。
2. **AI 客服无真实模型**：纯关键字规则引擎，全仓无 LLM 客户端。「智能」名不副实，无多轮/意图/RAG。详见 §3.2、§5-②。
3. **触达渠道半截 + 用户资料缺字段**：短信/推送为桩；`UserDTO` 无 email/deviceToken，邮件默认只能靠请求带 `targetEmail`。详见 §3.2、§5-③。
4. **定时发布悬空**：`ChapterService` 定时发布等调度器但无 XXL-Job Handler 接管，到点不自动发布。详见 §3.4、§5-⑤。
5. **跨服务「共享表」耦合债**：`commerce.com.moyue.author` 与 `system.com.moyue.operation` 双映射同一张 `author_income` 表（非 Feign）；真正跨服务写前读仅 `RewardService→BookClient`。建议收敛为事件/Feign。
6. **书架同步非实时**：靠共享表 + 缓存拉取，有 ≤5min 陈旧窗口（已知设计，非缺陷，但弱于 WebSocket 实时）。详见 `docs/时序图/书架同步.md`。
7. **分类硬编码**：`BookService.CATEGORY_NAMES` 写死 3 类，无独立分类服务/表。
8. **测试覆盖低且不均 + 4 个流程用例 @Disabled**：核心流程停用，弱覆盖模块无单测。详见 §3.3、§5-⑦。
9. **ES 本机未启动**：检索域依赖运行中 ES(8.13.4+IK)，本机未起；索引创建/查询在 ES 不可用时降级（不阻断主链路），但搜索功能实际不可用。
10. **文档与代码漂移（需修正）**：
    - README「九、路线图状态（P0→P2 已全部交付）」「P2-15 敏感词/机审/举报 业务代码待实现」均不准确——机审/敏感词/举报**已真实落地**；
    - README 称 Flyway「V1–V13/38 表」，实际落地 **V1–V15**（V12 system、V13 内容安全与触达、V14 字典配置日志、V15 敏感词命中统计与菜单）；
    - README 搜索仅提 `moyue_book`，实际有 **book / chapter / qa** 三套索引。
11. **网关「信任头」鉴权模型**：网关验 JWT 并注入 `X-User-Id`，下游 `HeaderInterceptor` 直接信任该头。若服务端口被直连（绕过网关）可伪造身份——需在可信网络内部署，或增加服务间 mTLS / 二次校验。
12. **契约工具链已建但无消费端**：`moyue-contract` 产出 TS 客户端到 `moyue-frontend/src/api/sample`，但 **无 `moyue-frontend` 项目**，前端契约尚未被真实使用。

## 7. 结论 TL;DR

**墨阅后端 11 个服务整体落地度较高、基建扎实（网关鉴权/Feign 熔断/ES 检索/IM WebSocket/机审 AC 自动机/统计聚合均真实可用），但存在三类必须正视的断点：① 稿酬仅打赏分成、结算打款与订阅分成完全缺失（最大商业闭环缺口）；② AI 客服是纯关键字规则、无 LLM；③ 短信/推送触达为桩且用户资料缺 email/deviceToken；另有时序图已明示的「定时发布无调度接管」、4 个 @Disabled 测试与文档漂移等技术债——建议以 P0（稿酬打款闭环 + 定时发布调度 + 测试基线）为先，P1 补齐 LLM 客服/真实触达/个性化推荐/内容安全闭环。**
