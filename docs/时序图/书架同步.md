# 时序图 · 书架同步（跨端 / 跨设备）

> 模块：`moyue-content` 的 `com.moyue.read`（ReadController / ReadService / BookshelfEntity / BookshelfMapper）。
> 阅读说明：**本时序图全部为已读源码确认的真实代码路径**。本服务**没有**显式的实时推送 / Redis 发布订阅 / 账户服务同步机制——"跨端同步"在现有实现中是通过**共享 per-user 数据表 + 网关注入的同一 `X-User-Id` + 拉取时读取最新行**隐式达成的（详见文末 Caption）。仅 `reportDuration` 存在真实的 Feign 跨服务调用。

## 真实路径：写入书架 / 更新进度（设备 A）

```mermaid
sequenceDiagram
    autonumber
    participant DA as 设备A(同userId)
    participant GW as 网关 moyue-gateway
    participant RC as ReadController<br/>(moyue-content)
    participant RS as ReadService
    participant BM as BookshelfMapper
    participant DB as bookshelf 表(共享库, 按 userId)

    DA->>GW: POST /api/v1/read/bookshelf  {bookId}
    GW->>RC: addToShelf(req, request)  [网关注入 X-User-Id]
    RC->>RS: addToShelf(requireUserId(request), bookId)
    RS->>BM: insert(bookshelf: userId,bookId,isDeleted=0)
    alt 唯一键 uk_user_book 冲突(曾收藏后取消留逻辑删除行)
        BM-->>RS: DuplicateKeyException
        RS->>BM: revive(userId, bookId)  [原生UPDATE置is_deleted=0]
        BM->>DB: UPDATE bookshelf SET is_deleted=0 WHERE user_id=? AND book_id=?
    else 首次收藏
        BM->>DB: INSERT INTO bookshelf(...)
    end
    RS-->>RC: void (幂等)
    RC-->>GW: R.ok()
    GW-->>DA: 加入成功

    DA->>GW: PUT /api/v1/read/bookshelf/{bookId}/progress  {chapterId}
    GW->>RC: updateProgress(bookId, req, request)
    RC->>RS: updateProgress(userId, bookId, chapterId)
    RS->>BM: selectOne(userId, bookId) → findActive
    RS->>BM: updateById(set lastChapterId=chapterId)
    BM->>DB: UPDATE bookshelf SET last_chapter_id=? ...
    RS-->>RC: void
    RC-->>GW: R.ok()
    GW-->>DA: 进度已更新
```

## 真实路径：其他端拉取最新书架（设备 B，即"同步"）

```mermaid
sequenceDiagram
    autonumber
    participant DBr as 设备B(同userId, 另一端)
    participant GW as 网关 moyue-gateway
    participant RC as ReadController<br/>(moyue-content)
    participant RS as ReadService
    participant CACHE as 本地缓存 READ_BOOKSHELF(TTL 5min, key=userId)
    participant BM as BookshelfMapper
    participant DB as bookshelf 表(共享库)

    DBr->>GW: GET /api/v1/read/bookshelf/{userId}
    GW->>RC: getBookshelf(userId)
    RC->>RS: getShelf(userId)
    RS->>CACHE: @Cacheable(key=userId)
    alt 缓存命中(且<5min, 设备A的写入已使本key失效)
        CACHE-->>RS: 书架列表(可能含A的最新写入)
    else 缓存未命中/已失效
        RS->>BM: selectList(QueryWrapper.eq("user_id",userId).orderByDesc(create_time))
        BM->>DB: SELECT * FROM bookshelf WHERE user_id=? AND is_deleted=0 ORDER BY create_time DESC
        DB-->>BM: List<BookshelfEntity>(含设备A刚写入/更新的行)
        BM-->>RS: 最新书架
        RS->>CACHE: 写入缓存
    end
    RS-->>RC: R<List<BookshelfEntity>>
    RC-->>GW: R.ok(...)
    GW-->>DBr: 最新书架(跨端一致=读取共享表同一userId)
```

> 说明：设备 A 写入后 `ReadService` 用 `@CacheEvict(cacheNames=READ_BOOKSHELF, key=userId)` 失效了**该 userId** 的缓存，因此设备 B（同一 userId）下一次 `getShelf` 会回源数据库读到 A 的最新数据——这就是"同步"的实现方式：**无推送，拉取即一致**。

## 真实路径：阅读时长上报（唯一真实 Feign 跨服务调用）

```mermaid
sequenceDiagram
    autonumber
    participant DA as 设备A(同userId)
    participant GW as 网关 moyue-gateway
    participant RC as ReadController<br/>(moyue-content)
    participant RS as ReadService
    participant PC as PointsClient<br/>(Feign→moyue-commerce)
    participant PTS as PointsService<br/>(moyue-commerce)

    DA->>GW: POST /api/v1/read/duration {bookId, minutes}
    GW->>RC: reportDuration(req, request)
    RC->>RS: reportDuration(userId, bookId, minutes)
    RS->>RS: points = max(1, minutes/10), 上限120分钟
    RS->>PC: award(PointsAwardDTO{userId,bizType=2,points,remark})
    PC->>GW: POST /api/v1/internal/points/award (Feign name=moyue-commerce)
    GW->>PTS: 路由 lb://moyue-commerce → 内部积分发放
    PTS-->>PC: R<Integer>(新余额)
    PC-->>RS: R.ok(新余额)  [显式校验 R.code==0]
    RS-->>RC: 本次发放积分(失败返回0, 不阻断主流程)
    RC-->>GW: R.ok(points)
    GW-->>DA: 发放积分数
```

> 真实方法名（已核实）：
> - `ReadController.reportDuration(@RequestBody DurationRequest, HttpServletRequest)` → `ReadService.reportDuration(Long userId, Long bookId, Integer minutes)`。
> - `ReadService.reportDuration` 内：`PointsClient.award(PointsAwardDTO)` —— `moyue-api-commerce.PointsClient`（`@FeignClient(name="moyue-commerce")`），目标端点 `POST /api/v1/internal/points/award`，bizType=2（阅读时长奖励）。积分服务不可用时仅记 warn 返回 0，**不阻断阅读主流程**（旁路奖励）。
> - `ReadService` 注入 `PointsClient` 用 `@Autowired(required=false)`，故 content 模块未引 `moyue-api-commerce` 时该字段为 null，调用前判空。

### Caption（关键说明 / 假设）

1. **无显式跨端同步机制**：现有 `com.moyue.read` 代码中**不存在** WebSocket 推送、Redis 发布/订阅、或调用账户服务做多端同步的逻辑。跨设备一致性完全依赖：① 书架数据按 `userId` 存于**共享数据库**；② 网关为所有端的同一用户注入同一个 `X-User-Id` 头；③ 取书架是**拉取式** `getBookshelf(userId)`，读到的是该 userId 的最新行。即"同步 = 打开书架时读取共享表"。
2. **缓存导致的短暂不一致**：`getShelf` 有 `@Cacheable(READ_BOOKSHELF, TTL=5min, key=userId)`，写操作会 `@CacheEvict` 同 userId 缓存。若设备 B 在 5 分钟缓存窗口内且未触发任何写（不会自动失效），则最长可能看到 **≤5 分钟**的陈旧数据；设备 A 的写入会使 A 侧缓存即时失效，但**不会主动通知 B**。这是当前实现已知的同步延迟上限（设计观察，非缺陷）。
3. **幂等加书架**：`uk_user_book(user_id, book_id)` 唯一键 + 逻辑删除导致"收藏→取消→再收藏"撞键，`addToShelf` 用"insert 失败则 `revive` 原生 UPDATE"保证幂等（绕过 MP 逻辑删除过滤）。
4. **userId 不信任前端**：所有写接口（加书架/进度/时长）的 userId 一律取网关 `X-User-Id`（`Constants.USER_ID_HEADER`），只读接口 `getBookshelf` 的 userId 来自路径参数（属作者/读者自身数据查询，由上层业务保证授权）。
5. **真实跨服务调用**：仅 `ReadService → PointsClient.award`（Feign → `moyue-commerce` 内部积分端点）。图中的 `PointsService` 是该 Feign 目标端的占位名（实际为 commerce 模块 `com.moyue.points` 的积分服务），非 read 模块内部类。
