# 墨阅小说网 · 架构缺口补齐说明

> 配套文档：《墨阅小说网-系统架构设计说明书-V5.0.md》
> 适用范围：`moyue-cloud`（Cloud 版）/ `moyue-boot`（Boot 单体版）/ `moyue-web`（管理后台前端）
> 最近更新：代码工程脚手架落地阶段

## 一、为什么会有这份文档

架构说明书不可能穷举到「字段名、枚举值、方法签名」这一层。落地编码时凡是**说明书未定义但代码必须做出选择**的地方，都在本文显式登记并给出裁定，避免：

- 不同模块对同一枚举给出不同取值（如 `data_scope`）；
- 前端按猜测的路径调用后端（如操作日志到底是 `/operlogs` 还是 `/logs/oper`）；
- 新人接手时无法判断某个实现是「遵循规范」还是「随手写的」。

**编号规则**：`G-N`，编号在代码中以 `【架构缺口 G-N】` 注释回标，便于双向追溯。

## 三、契约对齐裁定（前端 vs 后端）

本轮做了一次**全量端点路径比对**（脚本扫描后端 `@RequestMapping` 与前端 `api/*.ts`），发现并修正了以下偏差。**一律以架构说明书为准**，前端改，后端不动：

| 域 | 说明书口径（= 后端） | 前端原写法 | 处理 |
| --- | --- | --- | --- |
| ⑦ 操作日志 | `/admin/system/operlogs` | `/admin/system/logs/oper` | 前端改 |
| ⑧ 登录日志 | `/admin/system/loginlogs` | `/admin/system/logs/login` | 前端改 |
| ⑧ 解锁账号 | `GET /loginlogs/unlock/{username}` | `PUT .../unlock/{username}` | 前端改为 GET |
| ⑨ 在线用户批量强退 | `DELETE /online`（body 传 tokenIds） | `DELETE /online/batch` | 前端改 |
| ⑩ 定时任务 | **只读**：列表 / 启停 / 触发 / 日志，**不提供增删改** | 有新增、编辑、删除按钮 | 前端移除写操作，改为只读页 + 健康探测降级提示 |
| ⑩ 启停 | `PUT /jobs/{jobId}/status` | `POST /jobs/{id}/start`、`/stop` | 前端合并为 status 接口 |
| ⑬ 缓存清理 | 只有「删指定 key」与「**按前缀**批量清理」 | 有「清空整库」 | 前端移除整库清空（生产风险过高），改为按前缀清理 + 二次确认 |

**说明**：说明书刻意不提供「清空 Redis 整库」与「前端维护 Cron」这两类高危能力，本轮选择**尊重契约**而不是图方便加端点——这两个口子一旦开了，出事故时没有回退余地。

## 四之二、P0 运行期缺陷登记（C 端 E2E 实跑暴露）

C 端域代码完成后，在 MySQL 8.0 + Redis 7 容器环境对 `moyue-boot` 做了 13 步端到端实跑（登录→建品→章节→书架→进度→评论→点赞→IM→WS）。
**再次验证「静态编译全绿 ≠ 能跑通」**，本轮暴露并修复 3 处仅运行期可见的缺陷：

| # | 现象（运行期） | 根因 | 修复 | 关联缺口 |
| --- | --- | --- | --- | --- |
| R-1 | 书架列表 500，`SQLSyntaxErrorException near '<if test=...'` | MyBatis **注解 SQL 不支持 XML `<if>` 动态标签**，标签被原样拼进 SQL | `BookShelfMapper.selectShelf` 改为 `(#{bookTitle} IS NULL OR #{bookTitle}='' OR ... LIKE ...)` 静态短路 | G-14 |
| R-2 | 取消点赞后再点赞 500，`Duplicate entry ... uk_comment_like` | 唯一键 `(comment_id,user_id)` **不含 is_deleted**，取消仅置 1，重新点赞直插撞键 | 与书架同策略 `reviveLike` 复活原行；判定用原生 `countAny`（MP `@TableLogic` 会隐藏已删行，导致误判后 insert） | G-15 |
| R-3 | WS 客户端连 `/ws/im` 握手被拒 HTTP 401 | `BootAuthFilter` 对非白名单路径强制校验 Bearer，而 WS 握手走 `?uid=` 订阅 | `application.yml` boot 白名单补 `/ws/im`（网关形态下同为放行） | G-17 |

> 端到端实跑结论：章节生命周期（草稿→发布、字数统计、目录）、书架幂等（连调 2 次仍 1 行）、进度 upsert（含书架最近章节同步）、
> 评论 CRUD、点赞切换 5 次（1→0→1→0→1，单行恒定）、IM 会话/消息/已读（未读 3→0）/撤回（status=2）、
> **WebSocket 定向广播（`BROADCAST_OK`）**、C 端 8 端点回归 **8/8 通过**、未登录访问被拒，全部达标。

## 四之三、Cloud 端到端缺陷登记（微服务形态实跑暴露）

Cloud 版在 MySQL 8.0 + Redis 7 + Nacos 2.3 容器环境完成了完整实跑（gateway 8080 + auth 8090 +
system 8086 + content 8082 + social 8083）。**上一段结尾预判的「同类风险最高」得到验证**——
微服务形态暴露出 9 处 Cloud 独有缺陷，其中 4 处足以让整条链路完全不可用。

| # | 现象（运行期） | 根因 | 修复 |
| --- | --- | --- | --- |
| C-1 | jar 仅 13K–245K，`java -jar` 报 `no main manifest attribute` | cloud 父 pom 同样非 `spring-boot-starter-parent`，且 9 个可执行模块都没配 repackage | 根 pom `pluginManagement` + 各可执行模块补 `spring-boot-maven-plugin`（产物 68M–160M） |
| C-2 | auth/content/social 启动即 `ERR AUTH <password> called without any password` | `RedissonConfig` 写了但**从未登记进** `AutoConfiguration.imports`；boot 靠 `@ComponentScan("com.moyue")` 侥幸生效，cloud 不扫全包 | 两仓 `common-redis` 的 imports 补 `RedissonConfig` |
| C-3 | 各服务日志打印 `moyue-boot`、端口抢 8080 | cloud 根目录残留 boot 版 `application.yml`，Spring Boot 对工作目录配置的优先级**高于** jar 内配置 | 删除（备份至 `/tmp`）；运行服务统一用独立工作目录 |
| C-4 | content 启动失败：`required a bean of type 'MetricsEndpoint'` | `MonitorAutoConfiguration` 只有 `@ConditionalOnClass(HealthEndpoint)`，而 `MetricsEndpoint` bean 受 `@ConditionalOnAvailableEndpoint` 控制——服务 yml 只暴露 `health,info` 时根本不创建 | 条件改为 `@ConditionalOnBean({HealthEndpoint, MetricsEndpoint})`（兑现注释承诺的降级语义）；cloud 三服务 yml 对齐 boot 暴露 `metrics` |
| C-5 | **全部经网关请求 404**，`path=/moyue-auth/api/...` | 9 个服务都带 `context-path: /moyue-xxx`，网关路由却是 `StripPrefix=0`，转发时不带前缀 | 每条路由补 `PrefixPath=/<service-id>` |
| C-6 | C 端书架、IM REST 接口经网关 404；7 个管理端前缀同样 404 | 网关路由表未随 P0 新增接口同步：`/api/v1/read/**`、`/api/v1/im/**`、`/api/v1/admin/{content,social,commerce,search,message,risk,ai}/**` 全部缺失 | 路由表补齐 9 个前缀 |
| C-7 | **所有业务异常都返回 HTTP 500**，前端拿不到业务码/提示 | `GlobalExceptionHandler` 在 `common-core`，cloud 不扫全包且 `common-core` **根本没有** `AutoConfiguration.imports` → 无任何 `@ExceptionHandler` 接管 | 新建 `CoreAutoConfiguration`（`@Import(GlobalExceptionHandler.class)`）并登记 imports |
| C-8 | `/ws/im` 握手 500，`ServletHttpHandlerAdapter` 出现在网关栈 | `common-security` 传递引入 `spring-boot-starter-web`，Boot 据此装配 `TomcatReactiveWebServerFactory`，网关变成「跑在 Tomcat 上的 WebFlux」，没有 Netty 的 WS 升级能力 | 新增 `NettyWebServerConfig` 显式提供 `NettyReactiveWebServerFactory`（`@ConditionalOnMissingBean` 让位），并强制 `WebApplicationType.REACTIVE` |
| C-9 | 换成 Netty 后 WS 仍失败 | Spring Cloud Gateway 转发 WebSocket 必须用 `lb:ws://`，`lb://` 生成的 URI 不兼容 | 独立 `moyue-social-ws` 路由，`uri: lb:ws://moyue-social` |

**附带加固**：`ImWebSocketHandler` 原先用 `?uid=` 识别用户，改一个参数即可冒用他人会话。现改为
**优先读取网关注入的 `X-User-Id` 身份头**（WS 握手本质是 HTTP 请求，网关已鉴权并注入），
仅无网关的裸连调试才回退 `?uid=`。

> **已知遗留风险**：boot 单体模式下 `/ws/im` 在白名单（见 R-3），过滤器不解析令牌也不注入身份头，
> 因此仍只能回退 `?uid=`，存在伪造风险。生产部署应走网关形态（cloud 已具备完整链路）。
> 若要单体直连，需让 `BootAuthFilter` 对白名单路径也尝试解析 `access_token` 并注入身份头——
> 因 WS 回调线程与过滤器线程未必相同，未在本轮改动，避免引入脆弱的线程假设。

> **Cloud 实跑结论**：39 项端到端断言 + 6 项 WebSocket 断言**全部通过**——
> 网关→Nacos→服务路由、JWT 转发、管理端 3 域、C 端内容/社交全链路、点赞幂等、IM 撤回、
> WS 经网关广播均在真实微服务环境下验证通过。
> **同一套 E2E 脚本在 boot 单体上同样 39/39 通过**，双仓「逐字节一致」的收益在此得到直接印证。

## 六、运行期缺陷修复登记（端到端实跑暴露的真实缺陷）

代码工程脚手架落地后，在有 MySQL 8.0 + Redis 7 容器的环境实跑了 `moyue-boot` 单体主链路。**静态编译全绿 ≠ 能跑通**——本次共暴露并修复 15+ 处仅运行时才暴露的缺陷。下表与《README-脚手架说明.md》5.2 台账一一对应，这里只登记「改变了契约/裁定」的项，并标注其归属的缺口编号，便于双向追溯。

| # | 现象（运行期） | 根因（契约层） | 裁定 / 修复 | 关联缺口 |

> **经验结论**：端到端跑通一次，比再补十个页面更能暴露真实问题。脚手架阶段的所有静态检查（编译、端点路径比对、前端自检）全绿，但真正启动并登录后才暴露出打包、Nacos、超管标识、Bean 冲突、MapperScan、字符集、Redisson、XXL-Job、Security 链、JWT claim、SQL 口径、`-parameters`、迁移缺列等一连串问题。**下一轮 Cloud 版端到端**是同类风险最高的未验证面（网关路由转发、Feign 跨模块、Nacos 注册发现均未在真实环境跑过），建议优先补齐。
